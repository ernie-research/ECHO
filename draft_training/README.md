# Drafter training

The ECHO-side code of the drafter training stack: the draft model definitions,
the trainer entry, and the launch configurations the paper's drafters were
trained with.

This is not a standalone package. It is the set of files this work adds to
[SpecForge](https://github.com/sgl-project/SpecForge), the public
speculative-decoding training framework, and it is published so the modelling
and the training configuration can be read, not so that `pip install` makes it
run. Everything else it imports — the data pipeline, FSDP wiring, the sglang
target engine — is upstream.

Cluster paths appear as `<WORKSPACE>` and host addresses as `<HOST_IP>`, the
same substitution the rest of this repository uses.

## What is here

- `specforge/target.py` — builds the target and the draft config, and loads the
  target. The target is always loaded **without its MTP layers**
  (`use_mtp=False`): the drafter is trained against the 24-layer backbone.
- `specforge/target_warmstart.py` — the warm-start path, which initialises an
  EAGLE-3 draft from the target's own pretrained MTP block instead of from
  scratch. The key mapping is in the comment block at the top.
- `specforge/modeling/draft/target_mtp_eagle.py` — the EAGLE-3 draft: one the target
  MTP block, a three-route feature fusion `fc` over capture layers `[1, 11, 20]`,
  an independent 32k `lm_head`, and the `t2d`/`d2t` vocabulary maps. 0.67B
  parameters.
- `specforge/modeling/draft/target_dspark.py` — the DSpark draft: five the target
  decoder layers reusing the backbone's layer type, plus a rank-256 Markov head
  and an acceptance-rate predictor. 2,220,183,041 parameters; the startup log
  prints it, and a different number means a different model was built.
- `specforge/modeling/draft/target_dflash.py` — the DFlash variant, the same
  five-layer body with `markov_rank=0`, so no Markov and no confidence head.
  2,117,159,168 parameters.
- `scripts/train_dspark.py` — the trainer. It dispatches the draft class on the
  checkpoint's `architectures` field, so the same entry trains all three, and
  takes `--accumulation-steps` for the configurations that cannot hold the
  global batch in one micro-step.
- `examples/` — one launch script per method, each pinning the global batch, the
  capture layers and the sglang target options used in the paper.
- `launch_split_6_3_3.sh` — the twelve-node launcher that trained DSpark,
  EAGLE-3 cold-start and EAGLE-3 warm-start side by side, six nodes and three
  and three, under one `mpirun`.
- `data_collection/` — how the training corpus was produced, below.

## The corpus, and how it was produced

The drafters are trained on assistant turns regenerated by the target itself on
open-perfectblend prompts, so the drafter learns the distribution it will have
to predict. `data_collection/` is that pipeline:

```
open-perfectblend prompts
  -> collect_perfectblend_sglang.py     generation against an sglang target
  -> part-*.jsonl                             96 shards, ~1.42M assistant turns
  -> convert_perfectblend_to_h5.py      tokenise and pack
  -> part-*.h5 + a .zy manifest               ds16 / ds16_lossmask / ds16_offset
  -> train_dspark.py --train-data-path <...>.zy
```

`run_collect_perfectblend_sglang.sh` and
`run_collect_perfectblend_12node.sh` are the two launchers. The converter
validates every row — `status=success`, user and assistant turns strictly
alternating, assistant last — and drops the rest; samples with fewer than
`2 x block_size` loss tokens (32 for DSpark) are filtered out. It runs
single-process and takes roughly half an hour to an hour over 1.42M rows.
`build_vocab_mapping.py` builds the `t2d`/`d2t` maps the EAGLE-3 draft's 32k
vocabulary needs, from a sample of the training set.

The prompts come from the public open-perfectblend set; the generated corpus
itself is not included, since it is the target's output.

## The global batch, and why the micro-batches differ

All configurations are trained at the same global batch of 48, which is 29,595
steps per epoch over the 1,420,572-row corpus, so their loss and accuracy curves
are comparable step by step. The per-rank micro-batch is not the same, and the
comment block at the top of `launch_split_6_3_3.sh` records why: the DSpark
draft measures 55 GiB per card at `B=1` on an 80 GiB card and does not fit at
`B=2`, while the 0.67B EAGLE-3 draft takes 26 GiB at `B=1` and 47 GiB at `B=2`.
So DSpark runs `dp=6, B=1` and EAGLE-3 runs `dp=3, B=2`, and both land on 48.

## Not here

The corpus, the target checkpoint and the trained drafter weights. The scripts
name the paths they expect; the quantities the paper reports are in
`benchmark_table/` and `figure_plot/`.
